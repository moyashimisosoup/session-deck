# Session Deck 初期構想

- 文書種別: CONCEPT / 初期構想
- 版: 0.1（2026-10-16）
- 状態: 構想段階。仕様・実装・連携可否は未確定
- リポジトリ: https://github.com/moyashimisosoup/session-deck
- 対象: ChatGPT / Claude Code / Codex / GitHub（必要に応じて拡張）

## 1. 目的と背景

ChatGPT、Claude Code、Codexなどを並行利用すると、同じ作業が複数の会話やセッションに分かれ、次の問題が起きる。

1. セッション名が不統一で、何を担当しているのか一覧から分かりにくい。
2. どのAI・セッションが作業中か、どこまで進んだか、誰が次に引き継ぐかが見えにくい。
3. 同じ作業を重複して始めたり、別セッションの未コミット変更と競合したりする危険がある。
4. チャットの移動・コンテキスト上限による交代時に、根拠や未完了事項を失いやすい。
5. Web、ローカル、スマートフォンから作業全体を同じ視点で把握しにくい。

**Session Deck** は、個別AIの会話を単に並べるのではなく、**作業（Work）とセッション（Session）を分離し、複数AIの担当・進捗・引継ぎ・証跡を俯瞰する管制盤**とする。

対象はTradingSystemに限定せず、複数のGitHubリポジトリや個人開発にも再利用できるものとする。

## 2. 設計原則

- **作業単位を主軸にする**: 1つの `work_id` に複数プラットフォームのセッションを関連づける。
- **正本と表示を分ける**: ChatGPT画面に見えるタイトルと、台帳上の正式名称は別に保持する。
- **事実と推定を分ける**: 「稼働中」「完了」「同期済み」は観測根拠なしに断定しない。取得不能や古い情報は明示する。
- **既存システムを尊重する**: GitHub、既存監視JSON、引継ぎ記録を読むアダプターを優先し、既存の監視・実行処理を重複実装しない。
- **読み取り中心から始める**: 外部への書込み、タイトル変更、セッションの開始・終了、Git操作は別権限の操作とし、明示的に有効化するまで行わない。
- **公開コードと非公開データを分離する**: 公開GitHub Pagesに秘密・非公開の会話情報を配信しない。
- **PC・スマートフォン対応**: 主要な閲覧・確認操作はiPhoneでも使用できるようにする。
- **追加課金を前提としない**: 既存PC・既存サブスクリプション・無料の静的ホスティングを優先する。

## 3. 主なユースケース

### UC-01: 作業全体を俯瞰する
プロジェクトごとに、着手前・進行中・確認待ち・引継ぎ待ち・完了・障害を一覧する。担当AIと最終証跡の時刻を表示し、元セッションやPR・Issueへ移動できる。

### UC-02: セッション名を統一する
正式名称を `【短い作業名】MMDD・作業番号・具体的内容` に統一する。名前を提案・検査し、変更可能な環境では明示的に許可された方法で変更する。表示名が変更できなくても、台帳の正式名称は保持する。

例: `【セッション管理】1016・SD-001・初期設計`

### UC-03: 複数AI間の引継ぎを安全にする
同一作業に属するChatGPT、Claude Code、Codexの各セッションを結び、担当、作業の区切り、Git状態、検証証跡、未完了事項、次の操作を記録する。引継ぎ文そのものは実行許可や完了証拠とみなさない。

### UC-04: 競合・重複を検出する
同じ作業IDに対する複数の書込み担当候補、未解放claim、同じブランチへの同時作業などを警告する。表示上の警告は独断でセッション停止・claim強制解除・ファイル削除を行わない。

### UC-05: 更新・停止を見分ける
最終観測時刻、情報源、更新遅延を区別する。しばらく更新がないだけで「停止した」と決めつけず「状態未確認」などの適切な表現を使う。

## 4. 全体アーキテクチャ（推奨）

```text
PC / iPhone
   |
   v
Web Dashboard（公開できる静的UI、GitHub Pages候補）
   |
   v
認証付きの非公開データ層（実セッション情報・状態履歴）
   ^
   | 読み取り/明示許可された登録のみ
   +-- GitHub: Issue / PR / Commit / CI（公式API）
   +-- Claude Code: Hooks / 既存セッション記録
   +-- Codex: 既存スキャン / 引継ぎ記録
   +-- ChatGPT Web: 任意導入のブラウザ拡張 / 手動登録
```

**Web UIを主、既存PCをローカル情報の収集補助とするハイブリッド方式**を基本案とする。

- **公開リポジトリ**: Web画面、サンプルデータ、スキーマ、テスト、ドキュメントなど公開して問題のないコードだけを置く。
- **GitHub Pages**: 静的UIの配信に使用可能。ただしサーバー処理や認証情報の秘匿はできない。公開URLを知っている人にも配信内容が見える前提で扱う。
- **非公開データ層**: 実際のセッションID、作業履歴、内部リンク、個人用メタデータを保持。候補は認証付きのストレージ/バックエンド、またはTailscale経由の自宅PC。実装方式は後で選定。
- **ブラウザ拡張**: ChatGPT Web版の会話IDと表示タイトルを利用者の明示的な操作で登録する。自動改名は別途実機検証のうえ段階的に導入。
- **ローカル収集**: Claude Code / Codexの既存Hooksや状態ファイルに接続する。秘密や会話本文を自動収集しない。
- **同期設計**: 収集データには情報源・観測時刻・取得結果・鮮度を付与し、重複を排除する。未確認の同期完了を表示しない。

> 注意: GitHub PagesのJavaScriptに個人用APIトークンや認証情報を埋め込まない。公開コードと非公開実データの混在は不可。

## 5. 管理データの概念モデル

### Project
- `project_id`: プロジェクト識別子
- `name`: プロジェクト名
- `repository_urls[]`: 関係リポジトリ（0件以上）
- `policy_refs[]`: 既存のMASTER、AGENTSなどの参照先

### Work
- `work_id`: 全AI間で共有する一意な作業ID（例: `SD-001`）
- `project_id`: 所属プロジェクト
- `title`: 作業名
- `description`: 完了条件・作業範囲
- `status`: `planned | active | waiting_review | handoff_ready | blocked | completed | unknown`
- `owner`: 人間の責任者または担当区分
- `claimed_by_session_key`: 書込み担当セッション（存在する場合）
- `links[]`: Issue / PR / 設計文書 / 証跡
- `last_verified_at`: 作業状態を根拠付きで最終確認した日時

### Session
- `session_key`: `platform + account_scope + native_session_id` に由来する内部一意キー
- `platform`: `chatgpt | claude_code | codex | other`
- `native_session_id`: プラットフォーム固有の識別子（取得できなければ未設定）
- `work_ids[]`: 関連する作業ID
- `canonical_title`: 正式なセッション名
- `observed_title`: プラットフォーム上で実際に観測した表示名
- `conversation_url`: 明示取得できた場合の遷移先（非公開データ）
- `session_state`: `active | idle | handed_off | ended | unknown`
- `last_observed_at`: 最終観測時刻
- `source`: 情報の取得方法、取得成否、確度
- `handoff_ref`: 引継ぎ記録の参照先
- `permissions`: 連携先で許可された読取り/書込みの範囲

### Event / Evidence
- `event_id`, `work_id`, `session_key`, `kind`
- `occurred_at`（事象時刻）、`observed_at`（取得時刻）
- `source_ref`（GitHubのSHA、実行記録、引継ぎファイルなど）
- `summary`（機密を除いた概要）、`verification_state`
- 事実、ユーザー申告、推定、未確認を明示的に区別する。

保存時刻はISO 8601（UTC）を原則とし、画面ではJSTなどに変換表示する。識別子にプラットフォーム間での互換性があるとは仮定しない。実データの公開可否はフィールド単位で判定する。

## 6. セッション命名規則

基本形:

`【短い作業名】MMDD・作業番号・具体的内容`

運用:
1. `work_id` を確定し、推奨名を生成する。
2. `canonical_title` を台帳に保存する。
3. `observed_title` が異なる場合は命名不一致として表示する。
4. 改名機能のある接続先でのみ、安全な操作方法と権限を確認して変更する。
5. 変更後は再取得して一致を確認する。失敗時に変更済みと報告しない。
6. 人間が意図的に付けたタイトルを自動で上書きしない（保護・除外設定を用意）。
7. 日付は正式名を採用した日を基本とし、セッション継続だけを理由に毎日更新しない。

ChatGPTの表示タイトルについて、一般のChatGPT会話を公式APIから一括取得・変更できる前提にはしない。ブラウザ拡張経由の改名は画面変更に影響を受けやすいため、検証・手動復旧・一時停止の手段が必要。

## 8. 実装フェーズ

### Phase 0: 設計と安全境界
- 本構想、スキーマ、データ公開基準を明文化する。
- 既存機能と重複する部分を洗い出す。
- 外部連携や自動書込みの権限を明確にする。

### Phase 1: 公開可能なWeb MVP
- GitHub Pagesで静的サイトを配信。
- **架空のサンプルデータのみ**で、作業/セッション一覧・検索・詳細・命名提案を実装。
- PCとiPhoneで表示・操作を検証。
- 認証や実データ連携はまだ実装しない。

### Phase 2: 手動登録と非公開データ管理
- 認証付き保存先を決定する。
- 手動でセッション・作業を登録し、IDを結び付ける。
- 操作ログ、エクスポート、同期競合の管理を用意する。

### Phase 3: 自動収集
- GitHub公式APIからPR・Issue・CI等の読取りを追加。
- Claude CodeとCodexの既存監視出力をアダプターから取り込む。
- ChatGPT Web版の拡張連携を任意導入とし、実機テストを行う。
- 重複作業・鮮度切れ・未引継ぎの警告を追加する。

### Phase 4: 安全な操作支援
- 正式名と表示名の不一致を訂正する支援。
- 人間による確認を挟む引継ぎ・担当変更。
- 操作の権限チェック、読戻し検証、取り消しや停止の手段。
- 複数AI間の依存関係・作業負荷・セッション寿命を可視化する。

## 9. 既存TradingSystemとの関係

TradingSystemには既に `scripts/session_lifecycle_monitor.py`、`config/session_lifecycle_policy.json`、`docs/runbooks/SESSION_LIFECYCLE.md` が存在する。

- Claude CodeのStop hook、handoff、resume-check、claim/releaseなどの既存実装を再利用候補とする。
- Codexの定期scanやChatGPT会話の計測は実装済みと仮定しない。
- トークン数・コンテキスト上限は取得できた実測値だけを表示する。
- Session Deckの導入だけでTradingSystemのMASTER、AGENTS、注文・市場データ運用、既存claimの権限・手順を変更しない。
- TradingSystem内の執行判断や売買状態の正本は従来のシステム側に留め、Session Deckはそれを置き換えない。
- 既存の変更禁止・承認要件、認証情報の非取得、注文禁止などの安全境界を継承する。

## 10. 安全・プライバシー・権限

- 公開リポジトリと公開Pagesに、認証情報、会話本文、プライベートな作業情報、実環境のセッションID・会話URLなどを含めない。
- セッションや会話の読み取りは用途・対象・収集範囲を明示し、最小限のメタデータに限定する。
- ブラウザ拡張は必要最小限の権限を使い、認証Cookieやトークンを抽出・送信しない。
- ローカル監視データをWebに出す場合は、公開範囲の検査、必要に応じた匿名化、送信失敗時の扱いを定義する。
- 既存の権限と操作制限を緩めない。第三者の認証情報を使った収集、未承認の課金API、無人での注文・削除・deploy・セッション停止等は扱わない。
- 同期済み・完了・稼働中などの表示には、観測元と観測日時を伴わせる。
- 公開サンプルには実在の個人名、実作業名、非公開URLを流用しない。

## 11. MVP受入基準（案）

- GitHub Pagesで動作し、スマホ・PC両方から表示できる。
- 架空データで複数プロジェクト、3種類のAI、複数セッションを一覧できる。
- 作業とセッションが多対多で結び付く。
- 命名テンプレートに従う推奨タイトルを生成・コピーできる。
- 観測済み / ユーザー入力 / 未確認の区別が分かる。
- 進捗・ステータス・更新時刻が表示され、データの鮮度を誤認しない。
- 非公開データを公開サイトに同梱せず、外部連携なしでデモが成立する。
- 既存TradingSystemの設定・実行経路を変更しない。
