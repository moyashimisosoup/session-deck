# APP-001 継続的な命名管理・自動化ロードマップ

更新：2026-10-22 JST。対象は既存のSession Deck台帳とChatGPT Web用拡張。
この文書の保存・更新は機能の実装完了、実機合格、自動改名の許可を意味しない。

## 1. 正本と現在地

- 正式名は **`【短い作業名】MMDD・作業番号・具体的内容`** に統一する。
- PR #35（`b390a2b810daa81815de4912a10775606008077e`）は入力欄のtype属性省略への修正。命名CIは10件成功、未マージ。
- 従来の実機成功は、本体UIで先に改名ダイアログを開いた状態からの入力・保存・再読み込み保持まで。拡張からメニューを開く全工程は別途検収する。
- 実装再開時に取得したmainは `37fd18e72dac85d9125af2e3254eac12ed853401`。古い監査時点のHEADを編集の基準にしない。
- 既存の作業番号を使用する。APP-001はアプリIDであり、会話ID・作業番号とは別。節番号などから作業番号を再発番しない。

## 2. 命名規則を一つに保つ

現行コンソールと拡張の `【】` を維持する。記号の違いを理由に互換パーサー、形式バージョン、括弧変換、移行処理を作らない。既存の会話名を自動で上書きしない。

短い作業名1〜20文字、具体的内容2〜70文字、作業番号1〜30文字という現在の上限を共通生成処理で検査する。作業番号の空白・区切り文字、作業名の括弧・区切り文字、改行、無効なMMDDは拒否する。JSTの当日を初期値とし、会話との対応登録時の日付を固定する。日付が変わっただけで改名しない。

コンソールと拡張で同じ生成処理を使い、同一入力から同じ候補を出す。入力不足なら作業選択を求め、本文や直前の作業から推測しない。

`docs/CHAT_PROGRESS_BAR.md` などの配布例も同じ規則へ合わせる。GitHub文書を変えてもChatGPT側のプロジェクト設定が変わったとは扱わず、設定変更と読戻しは独立に確認する。

## 3. 初期段階の最小データ

最初から六つの独立した管理レコードを作らない。既存台帳の情報を利用者が選択・登録するローカルの写しとして、次だけを管理する。

| 情報 | 最小限の内容 |
|---|---|
| 作業情報 | 既存の作業番号、短い作業名、具体的内容 |
| 会話との対応 | 会話ID、選択した作業番号、採用したMMDD、登録時の表示名 |
| 改名状態・履歴 | 対象会話、変更前後の名前、時刻、画面での確認結果 |

既存の `sessionDeckNamerRecords` は消さず保持し、必要な追加履歴をブラウザ内に保存する。古い表記の解析・再生成のために別システムを作らない。対象の会話IDと作業番号を混同しない。同じ会話へ別の作業を暗黙に付け替えない。

現段階の保存先は `chrome.storage.local`。新しいクラウドDB、複数端末同期、大規模な台帳は作らない。ローカル保存とサーバー側の改名保持確認は別である。

## 4. Phase 0：拡張からの単一会話改名

最優先。#35の入力欄修正を再利用し、現在のChatGPT Webを専用テスト会話で観測する。

- 実際の対象行、起動ボタン、開いたメニューの関連を確認して修正する。推測したセレクタを増やし続けない。
- 対象会話の一意性をボタン選択より先に検査する。メニューや入力欄の対象が不明なら停止する。
- 通常の開始状態から「拡張の操作→メニュー→入力→保存→画面上の一致→再読み込み後の保持」を検収する。
- 正常系、別会話、曖昧な候補、入力欄の不一致、途中の会話切替に絞って回帰を追加する。

候補生成の純粋処理は並行して開発してよい。ただし、この工程の実機成功前に条件付き自動改名を有効化しない。

## 5. Phase 1：作業情報から候補を生成

拡張内で既存の作業を選択・登録し、正式名を自動生成する。登録操作自体では改名しない。登録内容と会話の対応を保存し、再読み込み・再訪問でも同じ作業から候補を出す。

受入：コンソールと拡張の生成結果が一致し、未登録なら選択を求め、前の会話の作業を別会話へ流用しない。作業番号の無断生成、本文の要約による補完はしない。

## 6. Phase 2：会話検出と確認型改名

新規会話のID確定、A→B、戻る・進む、再読み込み、同一会話への再訪問を認識する。現在のURLと対象行だけを確認し、本文や全履歴を収集しない。

- 対応する作業がある場合、正式名を表示し、確認ボタン1回で当該会話だけを改名する。
- URL変更はpopstateだけに頼らず、最小限の定期照合でSPAの切替にも追従する。候補表示・操作直前・保存直前の対象を確認する。
- 未登録、別作業、表示名を一意に取得できない会話は停止する。
- 登録時または最後に確認した名前と違う表示名は保護し、手動変更を上書きしない。
- 対応解除後は候補適用を停止する。同名の再適用で保存を繰り返さない。
- 表示確認だけなら `ui_observed` と記録する。再読み込み保持は別途実機で確認し、記録の存在だけで保持確認済みにしない。

受入は正常改名、対象違い、曖昧さ、再読み込み、再訪問、手動変更後、対応解除に集中する。複数タブ・画面差など未検証の環境は明記し、無制限の再試行をしない。

## 7. Phase 3：条件付き自動改名（確認型の実機安定後）

初期設定はOFF。この段階で初めて、作業番号・対象会話・予定名・許可状態を持つ最小の許可情報を追加する。まず1作業・1会話・1端末に限定する。

有効な作業別許可、現在の対象と名前の一意性、手動保護なし、未確認の処理なしをすべて満たしたときだけ適用する。同じ会話と同じ予定名へ繰り返し保存しない。許可取消・停止操作を用意し、失敗や結果不明時は停止して表示を再確認する。許可を復活させる自動復旧はしない。

受入：許可前は変更なし、許可後の単一会話だけ保存1回、手動変更を維持、取消後は変更なし。全会話巡回・一括改名は対象外。

## 8. Phase 4：必要になってから非公開連携を評価

既存Session Deck台帳・Private Session Vault/Journalとの接続を再利用する。継続的な複数端末運用が必要になった時点で、認証付き接続、競合制御、リース、フェンシング、復旧方式の必要性を評価する。Phase 0〜2の前提にしない。

ブラウザの権限を作業別の自動改名許可として扱わない。未公開API、Cookie、認証トークン、会話本文を取得しない。公開Pages・GitHub・CIへ実会話ID、非公開URL、実タイトル、実画面画像を入れない。

iPhoneネイティブアプリはWeb拡張と別評価とし、当面は候補生成・コピー・手動改名を利用する。

## 9. 小PRと完了の証拠

1. #35を再利用したメニュー修正と回帰。
2. 共通生成処理、最小の作業登録・対応、候補表示と切替検出。
3. この既存文書の簡素化と関連例の訂正。
4. 確認型の実機検収後、最小許可機構を別PRで実装。

各区切りのCHECKPOINTにHEAD、PR、CI、実機で確認した工程、未完了、次の1操作を残す。完成コード、GitHub保存、CI成功、PC実機動作、Web公開を区別する。実テスト出力と必要な差分だけを許可された監査へ渡し、テストの存在や計画書で成功を代用しない。
