# Session Deck 開発ロードマップ

版: 0.1 / 更新: 2026-10-17
状態: 計画案。実装状況はコミットと検証記録を優先する。

## 目標

ChatGPT・Claude Code・Codex・GitHubの作業を、AIごとの会話一覧ではなく共通の作業IDを中心に俯瞰できるようにする。安全な引継ぎと重複作業の発見を優先し、監視や改名の自動化は検証後に段階的に導入する。

関連文書: [初期構想](CONCEPT.md) / [連携設計](INTEGRATION_PLAN.md) / [検証計画](TEST_PLAN.md)

## 現在地（2026-10-17）

- v0.1: デモデータ付き静的Web UIを追加（index.html / styles.css / app.js）。
- 動作対象: PC・モバイルの現代的ブラウザを想定。実機検証は未完了。
- 保存: ブラウザのlocalStorageのみ。実サービスとは未接続。
- 公開: ソースを公開リポジトリに置く段階。GitHub Pagesの設定・公開成功は別途確認が必要。
- v0.1の「稼働中」は架空データのラベル。稼働・作業完了・同期の証拠ではない。
- この文書に挙げる機能は、未実装の項目を含む。

## Phase 1: デモMVPを完成させる（最優先）

**SD-001 UIの動作検証**
- PC Chrome/EdgeとiPhone Safariでホーム、作業一覧、セッション、引継ぎの4画面を確認。
- 検索、プロジェクト・担当AI・状態での絞込み、作業/セッション詳細、登録フォームを確認。
- データ初期化、再読み込み後のlocalStorage復元、JSONエクスポート、名前コピーを検証。
- キーボード操作・フォーカス・画面横幅320〜430px程度の使いやすさを確認。
- 受入: 主要操作が通り、致命的なレイアウト崩れや操作不能がないこと。

**SD-002 Web公開手順の確立**
- GitHub Pagesを使う場合、配信対象を`main`のルートに限定する方針を確認。
- 公開対象に架空データ以外が混入していないか検査し、Pages URLでスマホから表示確認。
- デプロイやPages設定の変更は、対象・変更内容を確認してから実施する。
- 受入: 公開されたページでデモが動くことを実URLで検証できること。

**SD-003 セッションの識別・命名設計**
- work_id / session_key / source IDの違いをスキーマとして固定。
- 正式名`【短い作業名】MMDD・作業番号・具体的内容`を生成し、命名差異を可視化。
- 「正式名」と「実際のチャット名」を明確に分離し、初期段階ではコピー支援のみ。
- 受入: 複数セッションが1つの作業に紐づき、変更はデモ台帳にしか作用しないこと。

## Phase 2: 実データの安全な登録と非公開管理

**SD-004 非公開データ保存先の選定（設計判断が必要）**
- 候補: ローカル＋Tailscale、認証付きクラウドDB/ストレージ。
- セッションID・会話URL・作業メモを公開Pagesへ同梱しない。
- 認証、閲覧制御、バックアップ、削除、複数端末同期、無料枠と将来費用を比較。
- 受入: 脅威モデルとデータ分類を文書化し、テスト環境で認証・アクセス制御を確認。

**SD-005 管理データ形式と監査ログ**
- Project / Work / Session / Evidence / Handoff / Claim のスキーマとschema_versionを定義。
- 手動登録、エクスポート・インポート時の検証、タイムスタンプと情報源を付与。
- 「観測済み」「ユーザー入力」「推定」「取得不能」を混在させない。
- 受入: 不正データの拒否、古い状態表示、データ移行試験ができること。

## Phase 3: 外部連携（初期は読取りのみ）

**SD-006 GitHub連携**
- Issue / Pull Request / Commit / CIを公式の読取りAPIから取得。
- work_idとURL・ブランチ・証跡を対応づける。レート制限と失敗時表示を実装。
- 受入: 対象リポジトリの最終更新と情報源を示せること。

**SD-007 Claude Code・Codex連携**
- TradingSystem既存の`scripts/session_lifecycle_monitor.py`とJSON状態をアダプターで読む。
- 既存の`claim`/`release`、handoff、resume-checkは再実装・無断変更しない。
- Codex定期スキャン、モデルのコンテキスト量は未確認のものを実測と称しない。
- 受入: 実データからセッションID、観測日時、情報源が得られること。

**SD-008 ChatGPT連携**
- Webブラウザ拡張・手動登録を先に検証。一般チャットを公式APIで一括管理できる前提は置かない。
- 読取り権限を最小限とし、認証Cookie・トークン・会話本文は取得しない。
- 実タイトル変更は互換性・復元・手動保護・読戻しが整うまで無効。
- 受入: 明示登録された会話IDと表示タイトルを台帳に安全に対応づけられること。

## Phase 4: 管理・引継ぎの高度化

**SD-009 競合警告**
- 同一work_idに対する書込み担当の競合、古いclaim、異なるブランチなどを警告。
- 「観測なし」を「停止」と断定しない。警告だけで強制終了・ロック解除しない。

**SD-010 安全な改名支援**
- 正式名/表示名の差異とユーザー保護ルールに従い、対象セッションのみ改名。
- 操作前の確認、失敗の記録、操作後の実名読戻し、手動復元経路を用意。
- 改名の実行権限は利用者が明示的に設定した接続先のみに限定。

**SD-011 セッション寿命・引継ぎボード**
- コンテキスト使用量などは取得できた環境の実測値だけを表示。
- 引継ぎ内容とGit・テスト証跡を別扱いとし、受け手の再確認を必須にする。
- セッションの無断停止・自動交代・作業開始を行わない。

## 優先順位と依存関係

1. SD-001 → SD-002: UIの実機検証を済ませてからPages配信確認。
2. SD-003とSD-005: IDと保存形式の確定が全連携の土台。
3. SD-004 → SD-006〜008: 実データ連携の前に非公開保存先と認証を決める。
4. SD-006〜008 → SD-009〜011: 信頼できる観測データと安全境界を得た後に管理自動化。
5. GitHub連携や外部認証で追加課金・追加権限が必要なら導入を止め、都度検討する。

## 完了の共通判定

- **実装済み**: コードが存在するだけ。
- **検証済み**: 試験の入力・実行日時・結果が残り、期待動作が確認できる。
- **配信済み**: 実URLから最新画面を読み戻して確認できる。
- **連携済み**: 実サービスから取得した情報の情報源・時刻・整合性が確認できる。

この4段階を混同しない。確認できない場合は「未確認」と記録する。

## 変更管理

- ロードマップは状況に応じて更新できるが、完了済みの証跡を上書きしない。
- 予定の期日・開発費・使用量は根拠なしに推測しない。
- TradingSystemのMASTER / AGENTS、注文、安全境界、認証とコミットの承認規則を変更するものではない。
