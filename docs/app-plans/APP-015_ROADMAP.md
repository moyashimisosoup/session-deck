## 0. 計画の結論

**語彙の完全校閲より、古語の文字推理ゲームを小さく成立させて実際に遊び、そこから入力辞書と解説を補強する。** 2モード（純粋推理／古典学習）は維持する。技術はHTML/CSS/JavaScriptによる静的Webアプリ、ブラウザ実行、GitHub Pagesでの配信を第一候補とし、ローカル環境のセットアップを前提としない。

**やらないこと**：アカウント、外部サーバー、課金、AI自動出題、完全な古語辞典、全語の学術的校訂、全活用形の入力受理、最初からの日替わり配信、学習履歴のクラウド同期、重厚なフレームワーク、複雑なCI。

## 2. 複雑さを増やさない語彙採用ルール（本書の最重要決定）

### 2.1 最小限の校閲

- **標準的な見出し語**：公開された信頼できる古語辞書・国語辞書等の**1項目**で、語の存在・歴史的仮名遣い（入力表記）・文字数を確認できれば、ゲームの**入力可能語**に採用してよい。
- **出題語**：上記に加え、学習モードで出す短い語義（1〜2個）・品詞に明白な誤りがないことを確認する。学習解説は自作の要約とする。毎語の2資料確認は不要。
- **表記差・時代差・同音異義・読みの異同・品詞の紛らわしさ**が現実に問題になる語だけ、追加の辞書・古典本文で確認するか一時保留する。検証の目的は「ゲームで誤解や誤判定が起こるか」に限定する。
- **不明な語**：無理に認めず `hold`。他の語へ差し替えて進む。保留語がゲーム公開を止めることはない。
- **資料と権利**：辞書の本文・語釈・大量のデータを無断複製しない。語形や独自に作った短い説明を、確認した利用条件の範囲で扱う。UniDic／コーパスを丸ごと収録することは別途許諾・規約確認が必要。

### 2.2 シンプルなステータス

- `draft`: 候補。出題も入力も未採用。
- `usable`: 語形確認済み。入力に使用可。出題に使うなら短いヒントも確認。
- `hold`: 問題あり。出題・入力から除外（表記差などは理由を記録）。

追加フラグ：`canGuess`（推理入力として許可）、`canAnswer`（正解として採用）。`canAnswer=true` なら必ず `canGuess=true`。

辞書出典の記録は、**資料名／確認URL（または書誌）／確認日／例外メモ**の最小限でよい。全語に詳細な出典作品・原文対校・歴史的な語義全列挙を義務付けない。

### 2.3 初期データの扱い

- v0.4の63語を**削除せず候補元**として使用し、簡素化後の採用欄を別途追加して移行する。
- 63語の全件再調査はせず、前回の参照記録を利用。明らかな曖昧語と保留語にだけ再確認を集中する。
- まず**正解20〜30語程度**で試作し、テストプレイで不足を感じた文字数・ジャンルから語を増やす。公開までに必要な語数は体験で決める。100語・500語という数値は**将来の拡充目標**に降格する。
- 入力辞書不足は重要なUX課題。アルファ版で判定UIを試す際は「語として存在するか」の厳格チェックを一時的に緩めてもよいが、**一般公開時は語の存在確認と入力却下理由の表示を行う**。プレイヤーがよく使う妥当な古語を繰り返し拒否するなら、語数の目標値に達していても未完成と扱う。

## 3. MVP（最初に完成させる製品）の具体的な仕様

### 3.1 必須

1. 純粋推理・古典学習モード切替。両者の成績・ヒント使用有無を混同しない。
2. 3〜5文字の歴史的仮名遣いの語をランダム出題。**1回6手まで**。長さは問題ごとに表示。
3. 緑＝位置も文字も一致、黄＝文字だけ一致、灰＝不一致。重複文字は**位置一致を先に割り当てる**。
4. NFCを基本とする入力文字列。`を/お`、`ゐ/い`、`ゑ/え`、`ぢ/じ`、`づ/ず` は別文字。文字数違い・辞書未登録語は試行数を減らさない。
5. 純粋推理：ゲーム前の語義・品詞ヒントなし。終了後に短い語義を表示。
6. 古典学習：ゲーム前に短い語義ヒント（必要なら品詞）、任意の追加ヒント、終了後の簡潔な確認カード。
7. ソフトキーボードで歴史的仮名遣いの特殊文字にアクセスできること。スマートフォンの日本語IME・確定入力にも対応。
8. 入力不可・正解・終了・残回数が**色以外の情報**でも分かること。
9. 成績はローカルストレージに保存。ログイン／クラウド送信なし。リセット可能。
10. オフラインでも既存ゲームが動くことは望ましいが、**初回正式公開の必須条件にはしない**（PWAは後回し）。

### 3.2 明示的に後回し

- 日替わり問題、ランキング、対戦、授業用配布機能、学習履歴の教師共有、全活用形を含む入力辞書、大量の用例・現代語訳、音声読み上げ、動きの多い豪華UI。
- テキスト入力のローマ字自動変換は、IMEと画面内仮名キーボードで不足すると分かった場合だけ追加。

### 3.3 UI演出方針

- 和紙を思わせるオフホワイトの背景、視認しやすい文字、控えめな配色。通常のWordleの意匠をそのまま複製しない。
- タイル出現（列ごとのスタッガー）、確定時のフリップ、正解時の軽い達成演出を候補とする。ただし**盤面の応答性＞演出**。
- `prefers-reduced-motion` を尊重。ユーザー操作を待たせる長いアニメーションを避ける。
- iPhone縦画面でゲーム情報と入力欄を無理なく使えることを優先。ピンチ操作や横スクロールは不要にする。

## 5. 検証計画（少数の重要テストだけ確実に）

### 5.1 自動テスト（ゲーム本体）

- 完全一致、1文字違い、位置違い、重複文字の消費順、余剰重複文字の灰色化。
- `を/お`、`ゐ/い`、`ゑ/え`、`ぢ/じ`、`づ/ず` の区別。
- 入力の文字数超過／不足、未登録語の回数非消費、6回で終了。
- `canAnswer` が `canGuess` に必ず含まれ、出題保留語が選ばれない。
- 同じ単語について、2モードの判定結果が一致し、ヒントと成績だけが異なる。
- リロード時の進行状態・成績の破損がない（仕様で途中状態を保存する場合のみ）。

### 5.2 手動テスト（配信と操作）

- Windows Chrome/Edge、iPhone Safariを優先。Android Chromeは追加確認対象。**未確認端末は未確認と表示する**。
- 文字のタップ、IME変換確定、特殊仮名入力、画面回転・小さい画面、キーボード出現時のレイアウト。
- 高コントラスト・視覚記号、キーボードのみでの操作、モーション低減。
- テスト利用者の「入力できるはずの古語が拒否される」「ヒントが曖昧」の2項目を重点記録。
- CI成功と実機操作成功は別証跡とする。Web配信成功でも実機未確認なら未確認のまま。

### 5.3 品質判定の現実的な基準

- **必ず止める**：文字判定が誤る、ゲームが進行不能、端末保存のデータ破損、公開データの無許諾転載、ログインや個人情報の意図しない送信。
- **公開前に優先修正**：iPhoneで入力しにくい、よく知られた妥当な古語を拒否し続ける、学習ヒントに重大な誤義がある、色だけでは判定不能。
- **公開後改善でよい**：辞書の希少語が少ない、解説が短い、演出のバリエーションが乏しい、学習帳や日替わり機能がない。

## 6. データの構造・更新手順（薄く始める）

最初は1ファイル `data/words.json` でよい。解答キーはひらがなの歴史的仮名遣い。異なる漢字・語義が同じ仮名なら、同一解答に簡潔な説明を複数紐づける（必要な語だけ）。

```json
{
  "id": "KW-001",
  "kana": "をかし",
  "length": 3,
  "canGuess": true,
  "canAnswer": true,
  "reviewStatus": "usable",
  "hint": "趣がある・おもしろい",
  "partOfSpeech": "形容詞",
  "source": "資料IDまたは参照先",
  "note": ""
}
```

- `source` は原文を複製せず、出典への参照を保持する。`hint` は独自表現。
- 語形検査はスクリプトで自動化（件数・重複・ひらがな・NFC・文字数・`canAnswer` の包含関係）。
- 新語追加は「候補→1辞書で語形確認→プレイ入力または出題として採用」を基本とする。問題がある語だけ要調査へ。
- 入力候補の追補は、実際の拒否例を優先して費用対効果を高める。全古語辞書の網羅は狙わない。

## 7. 公開方式・費用・権利

- GitHub Pagesは静的サイトの公開に使える。ユーザー別サーバー・DBはMVP不要。公開版はコード・データを見られる前提で、**秘密鍵・個人情報・非公開教材を入れない**。
- パブリックリポジトリのGitHub Pages配信を基本とする。すでに各アプリで使用している公開方法があれば再利用する。公開方法は公式資料で最終確認する。
- UI・アイコン・フォントはライセンスを明確にしたものだけを採用。仮称「古語Wordle」は開発上の識別名とし、正式な公開名は既存サービスと紛らわしくないものを選ぶ。
- 語義・辞書本文の丸写し、辞書・コーパスの一括再配布は避ける。研究コーパスと解析辞書は、公開ゲームへの組込み条件が確認できない限り補助的な参照に留める。
- 無料・低コストを基本とし、課金APIや有料DBは導入しない。GitHub Actions消費は、必要な単体テストだけに制限する。公開方式の変更にあたっては共有CIの既存運用に配慮する。

## 9. 管理・CHECKPOINTと引継ぎ

1. **中央台帳**は段階・最終根拠・次の一手だけ管理。細部はアプリRepoへ集約。
2. 書込み前に中央台帳と正本Repoの最新HEADを確認。既存資料の重複作成・並行編集の競合を避ける。
3. 正本Repo確定、試作完成、テスト公開、正式公開、重大な方針変更だけ台帳を更新。毎回の会話で更新しない。
4. 実装完了・コミット保存・CI合格・Pages配信・iPhone実機成功を**別々の事実**として記録する。
5. HANDOFF時には `APP-015`、正本Repo、branch/HEAD、目的、作業済み、検証済みと未検証、未保存資料、次の1操作を含める。
