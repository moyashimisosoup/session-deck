# Session Deck 連携・データ保護計画

版: 0.1 / 更新: 2026-10-17
位置づけ: 未実装の設計案。外部APIへの接続や同期を保証しない。

## 基本構成

静的フロントエンド（公開GitHub Pages候補） + 認証付き非公開保存層 + 情報源別アダプター（ローカル/ブラウザ拡張/API）を分離する。公開ソースコードから実利用者のデータ・認証情報へアクセスできない構成を必須とする。

デモ版は`localStorage`のみを使い、外部通信、ログイン、同期を行わない。ページ内の登録情報はブラウザ側にのみ保持される。GitHub Pagesなど共通オリジン上のlocalStorageはサイト間で共有され得るため、デモに実データを入れない。

## 情報源別の取得計画

| 情報源 | 最初に取得する内容 | 手段 | 留意点 |
|---|---|---|---|
| GitHub | Issue、PR、CI、コミットの識別子・状態・URL | 公式API、読取り権限 | 非公開リポジトリの可視範囲を限定 |
| Claude Code | セッションID、観測時刻、引継ぎ参照 | 既存Hooks/監視JSONの読取り | トランスクリプト・認証情報は収集しない |
| Codex | セッションID、観測時刻、引継ぎ参照 | 既存スキャン出力の読取り | 自動定期スキャンは未検証・既存処理を優先 |
| ChatGPT Web | 明示登録した会話ID、表示名、リンク | 任意のブラウザ拡張／手動登録 | 公式の一般チャット一括管理APIを想定しない |
| 人間の入力 | Workの目標、担当、引継ぎ状態 | 認証済みWebフォーム | 外部サービスの実状態とは区別 |

## IDの階層

- `project_id`: プロジェクト固有ID。
- `work_id`: AI横断で共有する作業ID。作業の正本識別子。
- `session_key`: システム内部のセッション識別子。プラットフォーム、接続範囲、ネイティブIDを区別する。
- `native_session_id`: サービスから実際に取得した固有ID（取得不可なら空欄）。
- `canonical_title`: Session Deckの正式名。
- `observed_title`: サービス画面で観測できた名前。
- `source_ref`、`observed_at`: 検証可能性を支える情報源と観測時刻。

異なるプラットフォームのネイティブIDを同一視しない。IDだけで同じ作業だと自動断定しない。

## 保存情報の分類

**公開可能**: UIコード、スキーマ、架空のサンプルデータ、一般的な設計文書、機密を除いたテスト結果。

**非公開**: 実セッションID・会話URL・内部作業名、Issue/PRの非公開情報、ユーザーの引継ぎメモ、観測日時の詳細、内部ログ。

**収集・共有禁止**: パスワード、APIキー、トークン、Cookie、MFA・PIN等の認証情報。証券取引や口座操作の実行権限も対象外。

静的公開サイトに非公開データをビルド同梱しない。GitHub Actionsのログにも秘密情報を流さない。

## 将来の非公開データ層に必要なもの

1. 認証済みユーザーとレコードのアクセス制御。
2. 最小権限の接続と権限の取り消し機能。
3. 読取り／更新／改名等の操作別の許可と監査。
4. 同期の競合解消、重複イベントの冪等処理。
5. オフライン状態、古い観測値、接続失敗の明示。
6. バックアップと復元、エクスポートと削除の手順。
7. 追加の有料サービスを導入しない初期案。

## 既存TradingSystemとの境界

- 既存`scripts/session_lifecycle_monitor.py`の出力を読み取る独立アダプターを優先。
- `config/session_lifecycle_policy.json`の閾値をSession Deck側で勝手に変更しない。
- 既存`claim`を取得・解除・強制上書きする操作はMVPに含めない。
- 引継ぎ記録や会話上の報告より、Gitの状態・テスト・受付票など一次証拠を優先。
- 実口座と仮想口座の状態は混同しない。注文・課金・認証変更・自動デプロイの権限を持たせない。

## 段階的な安全確認

- **Demo**: 公開前に通信・埋込データを監査。モックのみで動作。
- **Private storage**: アクセス拒否、本人認証、バックアップを試験。
- **Read-only integrations**: 取得範囲、情報源、鮮度、失敗経路を実証。
- **Writes / renaming**: 操作前確認、対象の一意性、読戻し、停止・復旧の方法が確認できるまで有効化しない。

設計を変更する際は、最小限の差分をレビューし、利用規約・権限・既存運用と矛盾がないことを確認する。
